# Content provider: recovered Windows loader contract

Phase A record for the authoritative content provider (server plan:
`BF-WorkingDirRust/docs/OFFLINE_CONTENT_LOADING_PLAN.md`). Recovered on
2026-10-03 from the x86 binaries with pefile + capstone, using the arm64
`libgame.so` (which has symbols) only for semantics. Every address below is an
**x86 RVA**; arm64 addresses are named as such. Updated 2026-10-05 (Session
11): the Phase C1 download-queue hooks (§2, §3.4), the prompt flag (§3.5), the
downloaded-name map global given as its RVA (§3.1; it had been written as its
VA), and the C1/C2 policy scopes (§6). Updated 2026-10-08 (Session 13): the
SuperAnim and particle read contracts (§3.7), the direct-`fopen` table
corrected (§3.3), and the C3 scope (§6).

Evidence labels: **x86-confirmed** (read from the Windows binary's code),
**arm64-semantics** (named function in libgame.so, matched to its x86 twin by
shared literals/call shape), **unit-tested** (tests/content_provider_tests),
**client-pending** (not yet observed in a running client).

The provider checks the three header fields of both loaded modules and the
masked bytes of every hook site (`OfflineMod.win32/content/cp_signatures.h`,
generated by `tests/fixtures/make_signatures.py`; bytes covered by a base
relocation are masked). Any mismatch declines **all** content hooks and logs
one line naming the field and the expected build; the game then runs exactly
as without the provider. The unit tests verify the table against the on-disk
binaries (`BF_APPX_DIR`) and that a changed byte or header declines.

## 3. Reader contracts

### 3.1 Existence ("is it downloaded?") — x86-confirmed

- `existsLocalFile(name)` (0x237EB0): empty name -> false. If the
  downloaded-name map exists (global at RVA 0x1597E20 -- written here until
  Session 11 as 0x1997E20, which is its VA: the instruction at 0xE417E5 encodes
  `mov esi, [0x01997E20]`), answer from it (0xE417E0: map
  lookup, value non-null; `Thumbs.db` and `.DS_*` always count as present).
  Otherwise `_stat64i32(writablePath + name) == 0` and `fopen("rb")` size > 0
  (0x237E50). `_stat64i32` has no other user.
- The map is built by enumerating LocalState (0xE415D0: `_findfirst64i32`
  / `_findnext64i32` POSIX-dir emulation, every name -> `CCInteger(1)`), at
  launch and by the login scene; the login scene (0x8E4330) also releases it,
  after which existence falls back to stat + size. Nothing compares a size,
  hash or version: a cached name is "downloaded" forever (matches the arm64
  `FileLoader::isFileAlreadyDownloaded`, but on Windows the fallback is a real
  file check).
- `getLocalPath(name)` (0x236950): `existsLocalFile` -> `writablePath + name`,
  else `existsBundleFile` -> `getResourcePath(name)` (the copy shipped in the
  package), else writable path + name.

### 3.2 Reads — x86-confirmed

- `getFileData` (0x135EB0): `fullPathForFilename(name)` (slot 14; absolute
  paths are returned unchanged), `fopen(path, mode)`, `fseek/ftell`,
  `new[]` (forwards to `msvcr120_app!operator new`), `fread`, `fclose`;
  `*size = fread count`, NULL + CCLog on failure. Callers free with
  `msvcr120_app!operator delete[]`. **Mode matters:** CSV readers pass `"r"`,
  so the CRT's text mode (CR LF -> LF, CTRL+Z ends the data) is part of the
  contract; `"rb"` is raw.
- `getCsvList(path)` (0x235C60, 41 callers: unit CGG/CGS, layouts):
  `getFileData(path, "r")`, split on LF.
- `getTexture` (0x2353D0): `setPopupNotify(false)`; up to 5 rounds of
  `CCTextureCache::textureForKey(path)`; `getFileData(path, "rb")`; if
  force-decode -> FileCrypt decode, else decode only a `.png` without
  `89 50 4E` / a `.jpg` without `FF D8`; `new CCImage`,
  `initWithImageData(data, size, 5, 0, 0, 8)`; on failure (and the path has no
  `.sam`) free, release and **retry with force-decode off**; else
  `addUIImage(image, path)`; `delete[] data`. FileCrypt decode is inlined
  (`data[i] -= i*i`), there is no separate function to hook.
- Two-image `getTexture` (0x65FB70, one caller 0xD7ACF0, used by 8 scenes):
  two `getFileData(.., "rb")` reads, both FileCrypt-decoded **unconditionally**
  (no magic check, no retry), merged side by side.
- SuperAnim: `LoadSuperAnimMainDef` (0x62B270) reads the `.sam` with
  `getFileData(path, "rb")`; on a parse failure it calls `remove(path)` and
  logs `Deleted corrupted file: %s`. Pages load through 0x632AC0:
  `CCSpriteFrameCache::spriteFrameByName(basename)` else
  `CCTextureCache::addImage(path)`; a missing page shows
  `CCMessageBox("<path> is missing.", "Error")`. arm64-semantics:
  `SuperAnimNode`'s destructor unloads its definition, so leaving and
  re-entering a scene re-reads the `.sam`.
- `CCTextureCache::addImage` (cocos 0x16A590): `fullPathForFilename`, cache by
  **full path**, `CCImage::initWithImageFile` (0x145AB0) ->
  `getFileData(.., "rb")`; `initWithImageFileThreadSafe` (0x145BA0) also uses
  `getFileData`. The game imports no `addImageAsync`.
- Town: `MyTownTopScene::initialize` (0xA51010):
  `existsLocalFile("MapVillage.sam")` -> `getLocalPath` -> SuperAnim node,
  else the bundled `MapVillage.sam`; same for `MapVillageAdd.sam`.

### 3.4 The download queues (Phase C1) — x86-confirmed, client-confirmed in use

- Scene demands go through `BaseScene::requestFileWithEncode` (0x63E270,
  `ret 0Ch`): it calls `existsLocalFile(name)` (at 0x63E2ED) and queues only
  an absent name -- with `addLoadFilePriority` (0x63E394) when the scene asked
  for priority (the list a `TransitionalDLCScene` downloads before the scene
  is entered), otherwise `addLoadFile` (0x63E3A9; the main list
  `FileLoader::update` works through when the background-download setting
  allows it). `addLoadFilePriority`'s other 32 call sites, in 12 functions
  (Town, land and gate, item lists, summons, mystery chest, arena, home),
  queue directly, and the function itself makes no call to `existsLocalFile`
  (the Session 10 handoff's "checks existsLocalFile itself" does not hold on
  x86).
- Hook rule (`Hook_AddLoadFile` / `Hook_AddLoadFilePriority`): while the
  provider is **active** and the flat basename of the queued path is owned
  **and present**, the entry is dropped and the by-value string is freed with
  the game's `msvcr120_app!operator delete` (the original would have
  destroyed it); the drop is counted (`suppressed downloads` in every perf
  line) and logged once per name (`not queued (provider serves it)`).
  Everything else -- provider starting, dormant or off, a name it does not
  own, an owned name it reports absent -- goes to the original unchanged, so a
  suppression can never strand a load the provider cannot replace. Entries
  from `requestFileWithEncode` never reach the hook for an owned, present name
  (its `existsLocalFile` already answered present); the suppressions are the
  direct callers. In the Session 10 client runs they were `MapVillage.sam`,
  `MapVillageAdd.sam` (Town queues its map itself) and
  `unit_ills_thum_50132.png`, up to 43 suppressions per process. (The comment
  on `suppressedEnqueues` in `cp_hooks_internal.h`, "this should stay 0",
  predates that evidence; it is left until the next DLL change so the
  reviewed source stays older than its binary.)
- **Observation (Session 16 DLL):** every name that passes through to the game's
  downloader is logged once as `QUEUED main` / `QUEUED priority` (up to 4,000 per
  list), and each scene change writes one totals line, `decisions (<kind>): ...`,
  counting every existence answer and enqueue decision by kind for that window and
  since start, plus how many assets and how many client-state names went to the
  main list. Per-name logging of owned answers is capped at 20 samples per kind:
  about 58,000 such lines cost some 20 s of a warm login before. Earlier DLLs
  logged no pass-through names; for their runs, which files a session downloaded
  is recovered offline from the package (Session 11, `BF-WorkingDirRust/out/qa/
  current/session11/trace_first_visits.py`, anchored by `keyDLC_WARNING_MENU_FLG`'s
  write time in `Settings\settings.dat`).

### 3.5 The background-download prompt flag

`DLC_WARNING_MENU_FLG` goes through `SaveUtils::saveUserDefaults` /
`loadUserDefaults` (RVA 0x23FFD0 / 0x240300; the Phase C1 plan first listed
their VAs 0x63FFD0 / 0x640300) into WinRT LocalSettings:
`%LOCALAPPDATA%\Packages\<package>\Settings\settings.dat`, value
`keyDLC_WARNING_MENU_FLG`, type 0x5F5E10C = UTF-16 string followed by the
FILETIME of the write. Yes stores `"true"`, No `"false"`
(`LoginScene::confirmAnswerYes/No` 0x8E6A80 / 0x8E6B00). The provider never
reads or writes `Settings\` itself. Since Session 16 the read at 0x8E51A8 goes
through the DLL (§9): it still calls the game's `loadUserDefaults`, a stored answer
always stands, and only when an Active provider holds a report proving complete
startup coverage for its generation, with nothing queued for background download,
is an unset answer read as `"false"` -- for that session, nothing stored. Otherwise the game asks, and the player's answer is stored by the
game as before.

### 3.6 What a screen draws, versus what it only asks for (Session 12)

A download or existence check does not show which file is drawn: a replacement
test must target the file the screen reads through `getTexture`. Unit
Archive, arm64 semantics (libgame.so), with the Windows evidence noted:

- **The tile.** `UnitDictionaryScene::setUnitDictionary` (0x17B3910) draws each
  unit as `GameUtils::getUnitListThum(id, UserUnitDictionary::getUnitImgType(),
  false)` (call 0x17B3EBC, DBB flag `w2 = 0`) through
  `GameScene::getCacheSpriteForLocal(2, ...)` (0x1622B60). That is the plain
  `unit_ills_thum_<id>.png` unless the alternate art is unlocked and selected.
  Windows: every Archive entry of Session 11 Run A served exactly the plain
  names through `getTexture` (caller +2354ED, inside 0x2353D0).
- **Its caches.** The sprite lives in the scene's own `UICacheList`
  (`GameScene`+0x210), gone with the scene. The texture is
  `CommonUtils::getTextureForLocal` -> `getTextureForAll` (0x1CE7A58):
  `existsLocalFile(name)` -> `getLocalPath() + name` -> `isFileExist` ->
  `getTexture(path)`, else `existsBundleFile` -> the bundled resource, else
  NULL. `getTexture` caches in `CCTextureCache` under that same path
  (§3.2); `TextureLoader` (`getTexture` 0xFBCB3C, `loadStart` 0xFBC8A4,
  `removeTextureForKey` 0xFBCE38) is a thin wrapper over it with the same key,
  not a second cache. So the safe point's `removeTextureForKey(path)` with the
  path `getFileData` was given (§4) is the complete invalidation.
- **`_100`** (DBB thumbnail) is drawn only where the DBB flag is passed. Of
  the 124 `getUnitListThum` call sites, 79 pass false; 43 pass
  `UserUnitInfo::isDbbEligible` (0x12B5EA4: unit in a DbbMst pair,
  rarity >= 8, extra-skill level > 9) or `BattleUnit::isDbbEligible` --
  owned-unit lists, party and battle screens; one forwards its caller's flag
  (`ColosseumMatchScene::setThum`); one is `requestUnitFiles` below. Never
  the Archive. `GameScene::requestUnitFiles` (0x160AF90) asks for
  `_100` (and `_2_100`) for every unit in a DbbMst pair, which is why the
  Archive checks and downloads it without drawing it.
- **`_2`** (alternate art): `requestUnitFiles` asks for the `_2` files when
  the dictionary row's flag is 1 (`2pAyFjmZ`, `UserUnitDictionary`+0x48) **or**
  `UnitMst` `jyj6bl9P` (ext_home_img_pos) is non-empty -- 60 unit types,
  owned or not, unlocked or not. A screen draws `_2` only when the flag is 1
  and the client-local selection (`+0x4C`, `getUnitImgType` 0x12B168C) is >= 2.
  Acquiring a unit adds a dictionary row with the flag 0: the plain art.
- **A withdrawn name** (absent from the provider): `existsLocalFile` answers
  absent, so the scene queues the game's own download (a Downloading screen;
  a tripwire write when it lands), and the draw then gets NULL from
  `getTextureForAll` because the provider still answers absent and never
  falls back to the LocalState copy. `GameSprite::init(NULL)` substitutes the
  2x2 `cc_2x2_null_image` texture (arm64 0xFE3FC8; x86 `test edi, edi` at
  +0x650F0C, the string push at +0x650F10): a blank tile, not a crash -- a
  static prediction, pending client observation.

### 3.7 SuperAnim definitions and particle plists (Session 13)

Full write-up: `BF-WorkingDirRust/docs/OFFLINE_CONTENT_PHASE_C3.md` §2.

- **Definition.** `getLocalPath(name)` (0x236950) -> `Load_GetSuperAnimMainDef`
  0x62C860 -> `LoadSuperAnimMainDef` 0x62B270: `getFileData(path, "rb")`, magic
  `MAS.` (0x62B44F, the only `.SAM` magic check in `.text`), version 1. x/y/w/h
  are 16-bit fields, or 32-bit when the caller passes mode 2 (arm64 `cmp w27,
  #2`, the unit and monster animations).
- **Pages.** `<directory of the .sam> + "/" + <image name>` (arm64 0xFF0BA4) ->

  `CCTextureCache::addImage` -> `getFileData` "rb". The path mixes separators
  (`...\LocalState/<page>`); `SplitLocalStatePath` folds them.
- **Dependencies, as the client computes them.** `addLoadFilePriority` records
  a `_dlcbundle` `.sam` in `XMLFileProcessor.xml`; `processSamAndCutSceneFile`
  0x106B10 -> `isFileExist(<LocalState>\X.sam)` -> `getSamSupportingFiles`
  0x62CBA0 (`getFileData` "rb", the image table) -> `existsLocalFile(page)` ->
  `downloadBundlePriority` 0x660870 for an absent page. Its cleanup edits XML
  nodes only. A provider-owned definition is present to `isFileExist`, so its
  pages are looked up and, owned, never queued.
- **Particles.** `GameParticle::create` 0x629990 (the EXE's only

  "rt" -> `CCSAXParser::parse`. The texture is `textureFileName` beside the
  plist if that file exists, else the embedded `textureImageData`.
- Both families are cached raw, and the provider serves them raw (text-mode
  translated for "rt"). server-tested: every one of the 36,321 C3 names read
  through `Hook_GetFileData` with these exact paths and modes equals the CRT's
  read of the file (`BF-WorkingDirRust/scripts/test_content_family_live.py

### 3.8 Sounds: the audio reader (Session 15)

Every sound load -- effects and music -- goes cocos `Audio::PreloadSoundEffect`
(0x6320, renames `.mp3` to `.wav`) -> `MediaStreamer::Initialize` (0x2EB50, full
wide path) -> the game's `SGAudioHandler` (installed at startup by 0xEB0BD0,
vtable 0x1961B04) slot 0 = 0xEC0030, which renames back to `.mp3` and decodes the
whole file: `fopen_s(&f, path, "rb")`, `fread(buf, 1, 210, f)` until 0,
`fclose(f)`. With a handler set the cocos WAV reader (CreateFile2 / ReadFile) is
never used. `tests/fixtures/check_audio_reader.py` proves on the binary: one
reference to the `fopen_s` import slot in the whole image, the FILE* reaches only
`fread` / `fclose`, no other stream call. The game's sound manager (0x64EFC0)
unloads its oldest effect when its list is full, so sounds are re-opened.

The provider patches the three import slots (all or none; fread and fclose
first). `fopen_s` of an owned, present LocalState name in a read mode returns a
registered `MemFile` holding the pinned, digest-verified bytes; `fread` /
`fclose` serve it and pass every real FILE* to the CRT. Absent -> `ENOENT`
(never the cached copy); provider idle/dormant or unowned -> the CRT. Without
the patch, sound names (`.mp3`, `.wav`) are never owned. Cached sounds are
plain MP3 identical to game_content's (no FileCrypt). Policy:
`BF-WorkingDirRust/scripts/gen_audio_policy.py`
(`BF-WorkingDirRust/docs/OFFLINE_CONTENT_PHASE_C5.md`).

## 4. Threads, ownership, cancellation

- `getFileData` runs on the render (UI/GL) thread for scene code and on the
  game's worker threads (CCThread / pthread loaders); the provider is
  thread-safe and single-flight per file. The map lookup 0xE417E0 is called
  from a worker while it holds the game's mutex (0xE40DEE): that hook only
  does an in-memory lookup, never network.
- Buffers returned to the game are allocated with `msvcr120_app!operator new`
  (the heap cocos's `new[]` and the game's `delete[]` use); the proxy itself
  links the static CRT and never frees game memory with it. The string
  returned by `getWritablePath` is freed with `msvcr120_app!operator delete`.
- The game's read path has no cancellation; the provider bounds it instead:
  WinINet connect 1.5 s, receive 5 s, send 3 s; a busy file (`503`) is retried
  three times (30/60/90 ms); a transport failure opens a 3 s fast-fail window so
  a dead server cannot stall every frame. A failed read returns NULL with
  `*size = 0`, as a missing file does, and is logged with its path.
- Order of a provider read: hook -> LocalState prefix + flat name -> index
  lookup (owned / absent / not owned), taking the entry's identity (SHA-256
  digest) and the scene token together -> RAM cache keyed by that identity, or
  a broker fetch bound to it (`/file?p=<rel>&d=<digest>`; the bytes are
  verified against the **pinned** digest, not only the response's own
  `X-BFCP-Digest`) -> text-mode / FileCrypt form -> copy into a game-heap
  buffer.
- Safe points: `replaceScene`/`pushScene`/`popScene`/`runWithScene` adopt the
  pending index delta, advance the scene token, evict changed files from the
  RAM cache and call `CCTextureCache::removeTextureForKey` with the exact path
  strings the game used, so the next scene reloads them through the provider.
  Deltas are fetched by a background thread every second and are never applied
  mid-scene. A fetch still outstanding when the token advances delivers its
  bytes to the readers of the scene that asked for them but is never cached.

## 5. Raw versus encoded

game_content holds raw files. The provider:

- clears `getTexture`'s force-decode (DL) for owned paths through a custom-ABI
  thunk (stack and callee-saved registers untouched; unit-tested at register
  level), so the original takes its magic-number branch and decodes nothing;
- serves FileCrypt-**encoded** bytes to the two-image reader's two call sites
  (identified by return address), which always decode;
- serves raw bytes everywhere else (cocos `addImage`, SuperAnim, CSV);
- applies MSVC text-mode translation to `"r"` reads (unit-tested against the
  CRT's own `fopen("r")` + `fread`, including the real `unit_cgg_60956.csv`).

## 7. Known limits (Phase C/D work)

- Reads are synchronous on the caller's thread (as the original disk read
  is); there is no scene-closure prefetch yet.
- Scene coherence is enforced, not best effort: the broker keeps no old
  versions, so a file whose server copy changed after the scene pinned it
  (first read, an LRU-evicted file, or a broker restart with other bytes)
  answers 409 `version-unavailable` and the read returns `Superseded` -- NULL to
  the game, like a missing file, logged as `failing it until the next scene
  change` -- and repeated reads of it in that scene make no further request.
  The next safe point adopts and serves the new version. A scene that reads a
  file for the first time after an edit therefore sees it missing until the
  next scene change; Phase C's scene-closure prefetch narrows that window.
- The download queues are filtered, not replaced (§3.4): an owned, present
  name is never queued; anything else is queued exactly as before. A name the
  provider reports absent still makes the game try its own download; if that
  succeeds the write to LocalState is logged as a tripwire, and the provider
  still reports the name absent (what a drawn image then shows: §3.6).
- Unowned families keep the game's own flow, download screens and the
  background-download prompt included: scene layouts and buttons
  (`_dlcbundle`), audio and voice, item and sphere art, UI art, banners,
  scripts. Session 11 traced which of them the first visits download
  (`BF-WorkingDirRust/docs/OFFLINE_CONTENT_PHASE_C2.md`); Session 13 measured
  what C3 changes (2,532 of the 5,612 traced first-visit downloads owned) and
  mapped startup (`BF-WorkingDirRust/docs/OFFLINE_STARTUP_TRANSITION_PLAN.md`).
- At C3 scale the 32-bit provider spends about 25 MB of private memory on the
  index (53,766 names), and a replace takes the broker 45-54 s to publish.
- `remove()` of an owned name's cached copy is refused (returns -1) and logged.
- The downloaded-name map keeps LocalState's names; only owned names are
  answered by the provider.

## 9. Startup coverage decisions (Session 16, corrected after QC; attach order Session 17)

`OfflineMod.win32/content/cp_startup*.{h,cpp}`, removed before the provider
(main.cpp `DetourDetach`: `Startup_Detach`, then `ContentProvider_Detach`). Its sites are
`kStartupSignatures` (9 sites, `tests/fixtures/make_signatures.py` `STARTUP_SITES`: the
census, its three call sites, the map lookup, `existsLocalFile`'s null-map fallback, the
prompt read, `loadUserDefaults` and its exit), and the content provider detours one of
them -- the map lookup 0xE417E0 is also its `isFileAlreadyDownloaded` site. So the
attach is two steps (Session 17; the C16 client of October 21 logged `DECLINED:
censusLookup: ... byte +0 is E9, expected 55` when the sites were checked only after the
provider):

1. `Startup_Prepare`, before `ContentProvider_Attach`: the module identity and every
   site's masked signature on the untouched image; the bytes of every site are kept
   (`cp_core.h SnapshotSites`).
2. `Startup_Attach`, after it: every site must still hold exactly those bytes, masked
   ones included, except where `kSharedSites` expects a detour -- only `censusLookup`,
   and only the provider's recorded `isFileAlreadyDownloaded` detour (`hooks::Env::detours`,
   filled after its commit). There the bytes must be exactly that detour (E9 to the
   provider's hook, CC to the end of the displaced instructions), the provider's
   trampoline must hold exactly the displaced original bytes followed by a jump back to
   the next instruction, and every other byte must be unchanged (`cp_core.h
   VerifySitesSince`). Then the prompt call must be `E8` targeting `base + 0x240300`, and
   both edits go in, the decisions bound to the provider last.

Any mismatch -- another build, a changed byte, a jump anywhere but the provider's hook, a
missing or misplaced detour, a trampoline that does not resume the original -- logs one
`startup coverage path DECLINED: ...` and the game keeps both, stock.
`tests/fixtures/check_attach_overlap.py` proves on the binary and the sources that
`censusLookup` is the only site any patch of this DLL reaches before its check (the
provider's lookup detour changes exactly bytes +0..+4 there), that no two patches touch the
same byte, and the attach and detach order. Composition: `Hook_IsFileAlreadyDownloaded`
answers an owned name itself and hands every other name to the trampoline, i.e. to the
original's own first instructions and then its unchanged remainder -- the null-map test
the left-out census relies on included.

| Site | Edit | Decision (per call) |
|---|---|---|
| census 0xE415D0 | Detours, its own transaction | left out only when the provider is **Active** -- checked before the report is used and again after it arrives -- and `GET /offline_mod/content/v1/coverage?build=<TimeDateStamp-SizeOfImage-Entry>` **proves** completeness (below) for the provider's pinned epoch and generation, with no newer generation pending; otherwise the original runs and is timed |
| prompt read 0x8E51A8 | rel32 -> `Hook_PromptFlagRead` | the game's `loadUserDefaults` is always called; a stored answer stands; an unset one becomes `"false"` for this session (nothing stored) only under the census's condition **and** no asset queued to the main list since start (client state such as the text-dictionary ZIPs does not count); otherwise `""`, and the game asks |

**What counts as complete** (`cp_core.cpp ParseCoverage`, judged with the build the DLL
asked about). The report is read only when it is well formed: `bfcp 2`, `coverage 1`,
every header field (`complete enabled ready epoch generation policy manifest
manifest_build client_build build_match unknown excluded`) exactly once,
`manifest_error`/`reason` at most once, each `set <name> required N ok N absent N unowned
N missing N ambiguous N unavailable N` line complete and not repeated, only `P` rows
(set, a known class, a name) and `U` rows, and a final `end`. Anything else -- an unknown
field, the first Session 16 broker's `A` rows, a truncated body -- is unreadable, which is
not ready. A readable report proves completeness only when nothing in it contradicts the
claim: `complete 1`, enabled, ready, `build_match 1`, client and manifest build equal to
the DLL's own, `sha256:` policy and manifest digests and no `manifest_error`, `unknown 0`
and no `U` row, exactly the `login` and `background` sets, each with `required > 0` and
`ok == required`, no `P` row and no reason; and a report whose counts do not add up (a
set's classes against its required names, more `P` rows than a count, `U` rows against
`unknown`) proves nothing whatever it claims. A bare `complete 1` was enough before the
QC correction; it is not now. The harness (`BF-WorkingDirRust/scripts/content_provider_client_test.py
parse_coverage`) applies the same rule, and both judge the shared corpus
`tests/fixtures/coverage_reports.txt` (29 reports, among them QC's bare claim) alike.

Why leaving the census out is safe (x86, `tests/fixtures/check_startup_sites.py`,
55 checks, 6 mutations caught by `--negative`): the census takes no arguments and
returns nothing anyone reads; it is the only code that sets the map global (VA 0x1997E20,
CCInteger 0x1997E24; the releases 0x8E490D / 0xA04684 clear it) and every reader
null-checks it; with the map null
`existsLocalFile` 0x237EB0 checks the file itself (`_stat64i32`, then a non-empty
`fopen` 0x237E50), the lookup 0xE417E0 answers "not downloaded", 0xE427B0 inserts
nothing into the FileLoader's complete list and the ten-worker filter 0xE413A0 returns
at once on that empty list -- the state of a fresh package. The MST load and
corruption check, the text-dictionary channel, `setInitialUnits` and the login
requests are untouched.

Not ready -- stock -- when: no provider (the build was declined); the provider is not
Active -- dormant, still starting, or its start failed (the census rechecks at its next
call; QC found that a complete report while the provider was starting had sufficed); the
provider stops being Active while the report is fetched; a generation is pending; the
report describes another generation or epoch; the broker is older (404) or the report
unreadable; the report does not prove completeness (above). Log lines: `startup coverage
path installed for build ...`, `LocalState census #N LEFT OUT [caller +RVA]: ...` /
`... built [caller +RVA]: N name(s) in X ms (<why>)` -- `<why>` is `the provider has not
adopted an index yet (starting, or its start failed)`, `the provider is dormant (broker
switched off)`, `startup coverage incomplete: <the report's reason, or what it failed to
prove>`, a generation mismatch, or a fetch error --, `background-download prompt: the
player's stored answer "..." stands`, `... left to the player: <why>`, `... LEFT OUT:
<why>; read as "false" (No) for this session, nothing stored`.
